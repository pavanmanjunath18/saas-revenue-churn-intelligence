## 7. Analytics Layer (All 8 Models)

All models are materialized views built by running `sql/analytics/99_run_all_analytics.sql`.

### Model 1: `monthly_revenue_overview` (04_monthly_revenue_overview.sql)
Computes per-month: total MRR, ARR, active customer count, ARPA, NRR (%), GRR (%).
- **Depends on:** `mrr_movement_report`
- NRR formula: (prior_mrr + expansion - contraction - churned + reactivation) / prior_mrr × 100
- GRR formula: (prior_mrr - contraction - churned) / prior_mrr × 100, capped at 100%

### Model 2: `mrr_movement_report` (05_mrr_movement_report.sql) — THE CORE MODEL
Classifies every customer-month into exactly one of 6 movement types:
- `new` — first month with MRR
- `expansion` — MRR increased vs prior month
- `contraction` — MRR decreased vs prior month (still positive)
- `churned` — MRR dropped to 0
- `reactivation` — MRR returned after being 0
- `unchanged` — same MRR as prior month

**Key implementation detail:** Uses a **customer-specific date spine** (only months where the customer existed, not a global spine) to prevent false reactivation classification. Without this, a customer who signed up month 6 would appear to "reactivate" every month from month 1–5.

**Key SQL patterns:**
```sql
-- Customer-specific spine
WITH customer_months AS (
  SELECT customer_id, generate_series(
    date_trunc('month', min(started_at)),
    date_trunc('month', CURRENT_DATE),
    interval '1 month'
  )::date AS month
  FROM subscriptions GROUP BY customer_id
),
-- LAG for period comparison
mrr_with_prev AS (
  SELECT *, LAG(mrr_cents, 1, 0) OVER (
    PARTITION BY customer_id ORDER BY month
  ) AS prev_mrr_cents
  FROM monthly_customer_mrr
)
```

### Model 3: `cohort_retention` (06_cohort_retention.sql)
Computes retention % for each cohort (signup month) × period (0–23 months).
Output: 24 cohorts × up to 24 periods = up to 576 rows.
Used by: Cohort Retention page (heatmap).

### Model 4: `customer_health_scores` (07_customer_health_scores.sql)
Weighted composite score (0–100) per customer with 5 signals:

| Component | Weight | Signal |
|---|---|---|
| usage_trend | 30% | Session count trend last 3 months |
| payment_health | 25% | Payment failure rate last 90 days |
| support_calm | 20% | Inverse of open high-priority tickets |
| tenure | 15% | Months since signup, capped at 24 |
| feature_depth | 10% | Distinct features used count |

### Model 5: `churn_risk_segments` (08_churn_risk_segments.sql)
Assigns risk tier based on health score + recommended action:

| Tier | Score | Action |
|---|---|---|
| Champion | ≥85 | Upsell / case study |
| Low Risk | 70–84 | Quarterly business review |
| Medium Risk | 50–69 | Customer success outreach |
| High Risk | 30–49 | Urgent intervention |
| Critical | <30 | Executive escalation |

### Models 6–8: Helper/staging models
Built as part of `99_run_all_analytics.sql` — intermediate CTEs materialized for performance.

**Build all models:**
```sql
-- In psql or any SQL client connected to the database:
\i sql/analytics/99_run_all_analytics.sql
```

**Rebuild after data reload:**
```sql
REFRESH MATERIALIZED VIEW mrr_movement_report;
REFRESH MATERIALIZED VIEW monthly_revenue_overview;
REFRESH MATERIALIZED VIEW cohort_retention;
REFRESH MATERIALIZED VIEW customer_health_scores;
REFRESH MATERIALIZED VIEW churn_risk_segments;
```

## 11. Critical Technical Decisions

### Decision 1: NO CSS injection in Streamlit
**Why:** `header { visibility: hidden; }` and similar broad CSS selectors in Streamlit 1.35+ hide chart container `<header>` elements. The entire dashboard went blank with no charts visible. This was the hardest bug to diagnose.

**Rule:** `style.py` contains ONLY color token dictionaries and `chart_layout()`. Zero `st.markdown("<style>...")` calls anywhere.

### Decision 2: Customer-specific date spine in MRR movement
**Why:** A global date spine (all months for all customers) causes false `reactivation` classification. A customer who signed up in month 6 would appear to reactivate every month from month 1–5 on a global spine.

**Implementation:** `generate_series(min(started_at), CURRENT_DATE, '1 month')` per customer.

### Decision 3: `_clean_url()` strips `channel_binding`
**Why:** Neon PostgreSQL 18 adds `channel_binding=require` to connection strings. psycopg2 doesn't support this parameter — connection fails silently.

**Implementation:** Regex strips `channel_binding=[^&]*` from any URL before passing to SQLAlchemy.

### Decision 4: Materialized views (not regular views)
**Why:** The analytics queries over 50K rows are complex (window functions, CTEs). Regular views re-execute on every dashboard load, causing 3–8 second query times. Materialized views pre-compute and cache — dashboard loads in <1 second.

**Tradeoff:** Views must be manually refreshed after data reload. `REFRESH MATERIALIZED VIEW` command required.

### Decision 5: Entry point as `Home.py` (not `streamlit_app.py`)
**Why:** Streamlit uses the entry point filename as the sidebar nav label. `streamlit_app.py` shows as "streamlit app" in sidebar. `Home.py` shows as "Home".

**Consequence:** Streamlit Cloud app must be deleted and redeployed if you ever change the main file path.

### Decision 6: Weighted health score with 5 independent signals
**Why:** Single-signal health scores are easy to game and miss context. Using 5 independent behavioral signals (usage, payment, support, tenure, features) creates a more robust and interpretable model.

**Weights are intentional:** usage_trend (30%) is the leading indicator; payment_health (25%) is the strongest churn predictor; others provide supporting context.

### Decision 7: `ON CONFLICT DO NOTHING` in load_data.py
**Why:** Makes the loader idempotent — safe to re-run without creating duplicate data. Also handles partial loads without needing to truncate first.

Raw CSV (synthetic) → psycopg2 batch loader → 12 normalized PostgreSQL tables → SQL analytics layer (window functions, CTEs, materialized views) → Streamlit dashboard reading directly from Neon cloud DB.

**"What's the hardest technical problem you solved?"**
The CSS injection bug. `header { visibility: hidden; }` was hiding chart container elements in Streamlit 1.35+ because Plotly wraps charts in `<header>` tags. Everything appeared blank for hours before I identified the root cause through browser DevTools inspection.

**"Why materialized views instead of dbt?"**
Trade-off: dbt requires running a separate dbt process and managing a dbt project structure. Materialized views are natively supported in PostgreSQL and give the same performance benefit (pre-computed queries) with zero additional dependencies. For a portfolio project, it demonstrates understanding of the underlying concept. A production system at scale would use dbt.

**"How did you validate data quality?"**
Three layers: (1) Python dtype enforcement in `load_data.py` before insert, (2) 23 SQL assertions in `02_validate_analytics.sql` checking referential integrity and business logic constraints, (3) 20 pytest assertions in `test_data_quality.py` checking CSV schema, row counts, and cross-table consistency.
